# Colormaps, legends and drawing

Moved from `packages/niivue/AGENTS.md`; read it when working on colormaps, label tables, legends or voxel drawing. Paths are relative to `packages/niivue`. A section named here but not found lives in another file of this folder (see the topic list in `AGENTS.md`).

## Colormap conventions

**Colormap display window (`min`/`max`):** Some bundled LUTs (the `ct_*` maps, e.g. `ct_bones` 180..600 HU) declare a suggested `cal_min`/`cal_max` window in their JSON, and `lookupColorMap(name)` returns it on the `ColorMap`. `NVCmaps.withColormapWindow` fills whichever of `calMin`/`calMax` is not given from it: when `NVModel.prepareVolume` loads a volume by URL, in the `NVChunkedVolume` constructor (`loadChunkedVolume`; the streamed volume still samples its robust/global range unless both bounds were given, and the auto window fills only bounds still unset), and in `setVolume` only when the colormap differs from the volume's current one (callers such as nv-mcp `set_volume` and the UIKit bridge re-send the colormap with every update, which must not reset the user's window). A given bound wins; a non-finite one (NaN, or null from JSON callers such as nv-mcp) means the image's default and `NVCmaps.resolveDefaultWindow` replaces it with `robustMin`/`robustMax` (the header cal_min/cal_max, else the 2-98% data range; a streamed volume samples it even when a CT map sets the window). A volume added as an `NVImage` keeps its own window: it always carries both bounds, so none is left for the map (#395).

**Negative colormaps:** Enabled by setting `colormapNegative` to a non-empty string. `calMinNeg`/`calMaxNeg` default to mirroring `calMin`/`calMax`.

**`colormapType`** (`COLORMAP_TYPE` enum in `NVConstants.ts`):
- `0` MIN_TO_MAX: Maps [calMin, calMax] across LUT. `isTransparentBelowCalMin` controls below-threshold.
- `1` ZERO_TO_MAX_TRANSPARENT: Maps [0, calMax], transparent below calMin.
- `2` ZERO_TO_MAX_TRANSLUCENT: Maps [0, calMax], faded alpha below calMin.

Volumes apply in GPU shader. Mesh layers apply during CPU compositing (`mesh/layers/index.ts`).

**Label colormaps (one colormap per volume, issue #69):** A colormap is a label table iff its definition has a `labels` array (an empty one counts); there is no other classifier (`_` name prefixes are gone: `draw`, `itksnap`, `slicer3d`). `setVolume(i, { colormap })` and the load options are the only entry point for both kinds; `NVModel.applyColormap` derives `NVImage.colormapLabel` from `colormap` at load and on every `colormap` change (null for a continuous map), so treat `colormapLabel` as read-only. A NIFTI_INTENT_LABEL volume loaded without a colormap gets `Random`, which is generated, not read from JSON: `labelLutFor('Random', [globalMin, globalMax])` hashes each ID to a colour over the volume's whole range and always at least IDs 0..255 (ID 0 transparent; capped at 256x8192 IDs, dropping far negative IDs first so 0..255 stays; non-finite range ends and voxels are ignored), so the same ID matches across volumes. `NVModel.growLabelRange` widens (never shrinks) a generated LUT to the values the volume now holds, scanning every frame of `img` (`globalMin`/`globalMax` describe frame 0 only); `applyColormap`, `updateVolumeData`, `isDirty` commits (`_commitDirtyVolumes`), `recalculateCalMinMax` and `loadDeferred4DVolumes` call it, `NVChunkedVolume.applyAutoWindow` grows a streamed volume's LUT to its sampled range via `NVCmaps.grownLabelLut`, and a table colormap is left as defined. A streamed volume also grows per decoded brick, independent of the display window: the source loader's `onChunk` hook hands each decoded region to `NVChunkedVolume.growLabelsFromChunk`, which records its finite range (`NVCmaps.finiteLabelRange`) under any colormap, coalesces bricks that arrive together, and only when an ID falls outside a generated LUT assigns the grown LUT and calls `_updateGLChanged()` (the new LUT changes `chunkedDisplayKey`, so resident bricks re-stream with the new colours). The renderer's decoded tier re-serves held bricks without decoding them again, so `setVolume({ colormap })` calls `growLabelsToObserved()` on each chunked volume to cover IDs decoded under an earlier colormap. Label LUTs are dense over min..max and **wrap into rows of 256** (`LABEL_LUT_WIDTH`, `labelLutTexels` in `view/NVOrient.ts`; the shaders `texelFetch`/`textureLoad` at `(i % 256, i / 256)`), so ranges past the GPU's max texture width (8192 under SwiftShader) still upload. Orient shader uses nearest LUT lookup; `calMin`/`calMax`/`colormapType`/`colormapNegative` are ignored for label volumes. `addColormap` with `labels` defaults `I` to 0..n-1 and allows one entry; re-registering a name rebuilds the label LUT of volumes using it. `colormapNames(kind?)` filters by kind; `drawColormap` accepts only label maps whose IDs all lie in 0..255, none negative (`isDrawingColormap`, throws otherwise), and `drawingColormaps` lists them. Documents (v10+) save the colormap by name and embed runtime-registered definitions (`colormaps`); the registry is page-wide but a volume keeps the LUT compiled when its colormap was applied, so when another viewer has since re-registered that name, `serialize` embeds the table the volume shows under `<Name> 2`, `3`, ... (`documentColormaps.shownLabelColormap`); `documentColormaps.upgradeColormaps` turns a v9 compiled `colormapLabel` into a document colormap named `<volume> labels` and maps `_draw`/`_itksnap`/`_slicer3d`. When a label colormap has names (e.g. the built-in `draw` colormap), the drawing volume surfaces the human-readable label (e.g. `"11bladder"`) in the `locationChange` event's `string` field instead of a numeric fallback like `"draw:11"`. Mesh layers follow the same model, with one difference at load: `NVMeshLayers.applyLayerColormap` derives `colormapLabel` from `colormap` (sized to the layer's finite values). `loadLayersFromOptions` (so `loadMeshes({ layers })` and `addMeshLayer`) calls it only for a label colormap, so a continuous one (documents name the default `warm`) leaves the label table a GIfTI or CIFTI file carried. `setMeshLayerProperty` calls it when `colormap` changes and no `colormapLabel` comes with it, so resending the current colormap keeps the table. `addColormap` re-derives and recomposites the layers using a name when its old or new definition is a label table.

**Legend visibility (issue #350):** a volume or mesh lists its labels when `nv.isLegendVisible && item.isLegendVisible !== false` (`NVModel.collectLegendEntries`, `view/NVLegend.ts`); the per-item flag defaults to true. Volume and mesh entries share one flat legend, volumes first, no heading. Until v11 the legend read a `showLegend` nothing set, which compiled because `NVImage` and `NVMesh` carry a `[key: string]: unknown` index signature (follow-up issue); `documentLegend.upgradeLegendFlags` drops the per-item flag from v10 and older documents and renames signal `display.showLegend`. Large atlases: the font never shrinks; entries wrap into columns of contiguous labels (`legendGrid`, up to 40% of the canvas width), then all columns scroll together. When rows overflow, the wheel over the legend backing (`isInLegend`) scrolls it instead of the slice/zoom: `WheelEvent.deltaMode` sets the unit (pixel deltas are CSS px, times `effectiveDevicePixelRatio` over `layout.pitch`; a line is one row, a page `visibleRows`) and accumulates fractionally in `model._legendScrollRow` (transient, not saved) so small trackpad deltas add up; `computeLegendLayout` clamps and floors it to whole rows, and `scrollLegend` starts from the shown row (a value left from a longer legend would swallow the first scroll). A pointer-down on the scrollbar track pages (`legendScrollHit`; the only scroll on touch screens) and one on the thumb is consumed, so neither starts a camera drag. Each view computes the layout once per frame, reserves its `width`, then sets `x`; drawing, hit tests and the wheel area share its geometry (`backingRect`, `scrollTrack`). The scrollbar sits inside the backing, so the wheel works over all of it. Sizes come from the font it draws with (`LegendFont`: `fontRenderer.fontPx`, which holds `fontMinSize`, `fontScale` and DPR, and `measureText`), so a larger font cannot overlap columns. `NVModel.legendScrollRow` returns to row 0 when `legendSources` changes (identity of the listed volumes and meshes, plus the colormap key): a load, removal, colormap change or `loadDocument`. A redraw, a label toggle or a streamed table growing keeps the position. Grouped tables (collapsible bones/organs/vessels, one-click toggles) are deferred. See `examples/legend.html` (AAL, 116 labels).

**Hidden labels.** `NVImage.hiddenLabels` (label values, not LUT rows; per-item option, saved in NVD without a version bump) hides regions on both backends. `colormapLabel` stays pristine (the legend, centroids and document colormap embedding read it); the GPU reads `NVCmaps.shownLabelLut(vol)` instead, a copy with alpha 0 at each hidden value, memoized per volume so its identity changes only with the LUT or hidden set. Every label-LUT upload and key (`orientColormapKey`, `overlayColormapKey`, `chunkedDisplayKey`, PAQD `lut256`) goes through it, so a toggle re-uploads like a colormap change. Hidden labels stay in the legend as an outline in the label colour, drawn as one panel with `backBorder` (the panel shaders keep a single antialiased ring, so there are no seams and a translucent colour blends once; separate bars left seams, #478). With `interaction.isLegendToggleEnabled` (default false) a click on a volume entry's colour box toggles it (`legendHitTest` in `view/NVLegend.ts` reports `isOnBox`); a name click still moves the crosshair. Mesh and connectome entries do not toggle. Known limit: a streamed volume's coarse floor is a separate NVImage built once, so it keeps drawing hidden labels in 3D until bricks cover it (it ignores later colormap changes the same way). See `examples/vox.atlas.html`.

**Legend centroids are lazy.** Nothing computes label centroids at load (a label `colormap`, document load, mesh layer load); `LegendEntry.centroid` is a function that `view/legendCentroids.ts` evaluates on the first legend click and memoizes in a `WeakMap` keyed on the data array: `volume.img` for volumes, with `[colormapLabel, matRAS, _dataVersion]` as dependencies, and `layer.values` for mesh layers, with `[mesh.positions, layer.colormapLabel, mesh._positionsVersion]` as dependencies. A dependency is compared by identity, so replace these objects, never mutate them in place (the version counters cover the in-place edits `updateVolumeData` / `updateMeshPositions` make); `applyVolumeTransform` and `resetVolumeAffine` assign a new `volume.matRAS` without touching `img` or the LUT, which is why `matRAS` is a dependency. Volume centroids are means of RAS voxel coordinates mapped through `matRAS` once; mesh centroids are means of vertex positions, already in mm. `LUT.centroids` no longer exists. A 256³ scan is ~60 ms (Chrome), down from 515-850 ms when it ran eagerly on every label load.

## Drawing (voxel bitmap editing)

Voxel-level drawing/annotation on 2D slices, visible in both 2D and 3D views. Module: `src/drawing/`.

**Data model:** `model.drawingVolume` is an `NVImage | null` — a proper NIfTI volume with its own header and RAS transforms. Its `img` field (`Uint8Array`) holds label indices (0 = transparent) matching background volume's `dimsRAS`. Converted to RGBA via `drawingBitmapToRGBA()`, uploaded as 3D texture. Use `Drawing.getDrawingBitmap(vol)` to access the bitmap. `Drawing.createDrawingVolume(back)` creates an empty drawing from a background volume.

**Undo:** Circular buffer of RLE-compressed (PackBits) snapshots, controller-owned (not serialized). `addUndoBitmap()` saves *before* each stroke. `drawUndo()` loads then decrements (load-then-decrement order). The public `drawAddUndoBitmap()` (and `ctx.drawing.pushUndo()` on the extension context) pushes the same snapshot, so an edit made through `ctx.drawing.update()` — an extension's wand, slice interpolation — can join the undo stack; push once per committed edit, not per hover preview.

**Persistence:** `drawingVolume` lives in model, survives view reinitialization. NVD documents serialize bitmap via RLE (v6). Undo buffers not persisted.

**GPU pipeline:** Drawing texture has its own binding slot, separate from overlay. `refreshDrawing()` sets `_drawingDirty` flag, deferred to RAF. `_flushDrawing()` does bitmap→RGBA + GPU upload once per frame. `updateDrawingTexture()` reuses existing texture (no bind group recreation).

**`draw.isFillOverwriting`** (default `true`): Controls whether pen/fill overwrite existing non-zero voxels. When `false`, skip already-colored voxels (eraser always works).

**`draw.isEnabled` vs `closeDrawing()`**: `draw.isEnabled = false` disables pen but keeps drawing visible. `closeDrawing()` destroys drawingVolume and GPU textures.
